# 义工平台（ZVP）新人上手访谈 20 问

> 版本 v2（2026-11-05）：从「知识点问答」改成「能力导向」。
> 上一版考的是「知不知道某个名词」，这一版考的是「遇到没见过的状况时，你会怎么想、怎么验证、怎么取舍」——后者更能反映真实水平，也不容易被背题蒙混。
> 用法：面谈时口述，允许追问、允许回答「不知道」。重点听推理过程，不看结论对不对。
> 评价看四件事：**证据意识**（先证实再改）、**边界意识**（失败/并发/数据量）、**取舍能力**（知道代价）、**自省能力**（知道自己不知道什么）。

---

## 一、排障与证据（1–5）

### 1. 线上接口突然大面积 500，你手上只有一个 URL 和一句「刚才还好好的」。接下来十分钟你干什么？
**想量**：事故中的优先级与证据链。
**好答案的样子**：
- 先划范围：全部接口还是某几个、所有用户还是某一类、所有机器还是某台。
- 抓一个具体失败请求，看响应体和后端 traceback（traceback 才是根因，状态码只是症状）。
- 对齐时间点，问「那之前发生了什么」：发布、配置变更、证书过期、磁盘满、依赖服务挂了。
- 先止血（回滚/摘流量/降级）再定位，每一步都说得出为什么。
**要警惕**：上来就猜原因；直接重启碰运气；在事故中改代码赌一把；没有验证手段就宣布修好了。

### 2. 一个 bug 只在生产出现，本地怎么都复现不了。你怎么缩小范围？
**想量**：对比思维与二分能力。
**好答案的样子**：
- 先列出「生产有、本地没有」的差异：数据、配置、版本、时区、并发量、外部依赖、权限。
- 用二分切：按用户/租户、按时间、按请求特征、按部署实例，每次切掉一半可能性。
- 加临时观测点获取事实，而不是靠读代码猜；构造出最小复现再动手改。
**要警惕**：「多加点日志看看」但说不出要看什么；改一处试一次，每次换一个猜测。

### 3. 用户说「页面很慢」。这句话信息量几乎为零，你会问什么、测什么？
**想量**：把模糊问题变成可度量问题的能力。
**好答案的样子**：
- 先问清：哪一屏、哪一步、多少人遇到、什么时候开始、稳定复现还是偶发、P50 还是 P99。
- 在浏览器 Network/Performance 里看时间花在哪一段：DNS、TLS、请求等待（TTFB）、下载、解析渲染。
- 定位到某个请求后再往服务端查：应用耗时还是慢查询，是不是只在特定数据量下慢。
**要警惕**：不看数据就下结论（「优化一下 SQL 吧」）；拿「我的电脑上挺快」当结论。

### 4. 你怀疑「数据不一致是缓存造成的」。怎么证实或推翻这个怀疑？
**想量**：是否会设计可证伪的验证，而不是先改再说。
**好答案的样子**：
- 绕过缓存直查源数据，对比同一时刻两边的值。
- 检查 key 的命名空间/版本号，确认写入后到底有没有失效、TTL 有没有重置。
- 区分三种可能：压根没失效、失效了但读到旧值（读写竞争）、根本不是缓存的问题。
**要警惕**：先改 TTL 试试；把「有缓存」默认当成 bug 来源。

### 5. 线上数据库 CPU 打满，你的处置顺序是什么？
**想量**：先恢复再优化，以及生产操作的克制。
**好答案的样子**：
- 止血：限流、降级、终止失控查询，先让业务能用。
- 定位：看当前会话和慢查询，看执行计划，判断是缺索引、统计信息陈旧、连接池打满，还是某个批量任务。
- 防复发：补告警和审计，找到触发条件而不是只处理这一次。
**要警惕**：第一反应「加机器」或「删点数据」；不看执行计划就建索引；在高峰做结构调整。

## 二、设计与取舍（6–10）

### 6. 什么情况下**不该**用缓存？缓存最危险的地方是什么？
**想量**：是否理解缓存的代价，而不只知道收益。
**好答案的样子**：
- 不该用：要求强一致、写多读少、命中率低、失效逻辑说不清的时候。
- 真正危险的不是「慢」，而是**旧值被当成真值**：穿透、击穿、雪崩、写完立刻读到旧数据，这些都要提前设计。
- 能说清失效策略（何时写、何时删、删失败怎么办）。
**要警惕**：「加个缓存就快了」的单一思路；说不出失效策略。

### 7. 「给这个字段加个索引，查得快点」——这条建议在什么情况下是错的？
**想量**：对索引成本与优化器行为的实际理解。
**好答案的样子**：
- 写多读少、区分度极低（比如性别）、已有组合索引能覆盖时，加索引只是拖慢写入、白占空间。
- 还要看优化器会不会真的走：返回行数占比太高就不走，统计信息陈旧也不走，列上有函数或隐式类型转换照样用不上。
**要警惕**：见到慢就建索引；不看执行计划；不理解「索引也是数据」。

### 8. 什么时候你会选择重复代码，而不是抽一个公共函数/组件？
**想量**：对抽象成本的判断力。
**好答案的样子**：
- 抽象的成本是「以后每次改动都要穿过这层间接」，所以只在「未来会一起变」时才抽。
- 两处长得像、但会朝不同方向演化，重复反而更便宜；判断依据是变化方向，不是当下的相似度。
**要警惕**：把「代码重复」当成唯一标准；为了复用塞一堆布尔开关做成万能组件。

### 9. 一个需求做到一半，你发现方案有根本性问题，已经写了两天。你说不说？怎么说？
**想量**：诚实的成本意识与沟通方式。
**好答案的样子**：
- 先自己验证这个判断，能举出具体反例或证据，而不是「感觉不对」。
- 尽早说，且带上完整信息：问题是什么、代价多大、我建议换成什么、已经写的能保留多少。
- 不隐瞒，也不把它包装成「再做两天就好了」。
**要警惕**：「再改改也许能行」拖到最后；或者一言不发推翻重来。

### 10. 一个接口从 200ms 变成 2s，你的怀疑顺序是什么？
**想量**：分层排查的技术储备。
**好答案的样子**：
- 按一次请求经过的层逐层排：客户端/网络（DNS、TLS、跨地域）→ 接入层（限流、排队）→ 应用（线程池/事件循环被阻塞、GC、外部调用超时）→ 数据库（慢查询、锁等待、连接池耗尽）→ 数据量本身变了。
- 关键是用耗时打点把范围缩到某一段，而不是逐层猜过去。
**要警惕**：只怀疑数据库；没有分段观测就开始改。

## 三、并发与故障边界（11–14）

### 11. 一次写操作要改两张表（或调两个服务），中途失败了怎么办？你能接受哪种不一致？
**想量**：对「原子性」边界的理解。
**好答案的样子**：
- 先明确业务能不能接受部分成功，再选手段：单库用事务；跨服务用幂等 + 补偿/对账，或本地消息表做最终一致。
- 关键是可观测、可重放、有对账，而不是假装它原子。
**要警惕**：以为「包个 try/except」就安全；跨服务也幻想强一致。

### 12. 你的写接口被前端重试了两次，可能发生什么？怎么防？
**想量**：重复提交的现实认识。
**好答案的样子**：
- 能数出重试来源：用户连点、浏览器/代理重放、客户端自动重试、超时但其实已经成功。
- 手段：唯一约束、幂等键、状态机只允许一次跃迁；并区分哪些接口可以安全重试、哪些绝对不能。
**要警惕**：只在前端加防抖就算解决。

### 13. 异步服务里有人写了一句同步阻塞调用（比如 `time.sleep`、同步 HTTP 客户端）。会发生什么？你怎么发现？
**想量**：是否真的理解事件循环，而不是把 `async def` 当性能开关。
**好答案的样子**：
- 阻塞会卡住整个事件循环，表现是「所有接口一起变慢、并发上不去，但 CPU 并不高」。
- 发现靠压测和事件循环延迟指标；修复靠换异步客户端，或把阻塞活儿丢进线程/进程池。
**要警惕**：认为加了 `async` 就自动并发；把「并发高但吞吐低」归因于机器不行。

### 14. 「本地跑通、测试全过」为什么不足以上线？你还会补什么？
**想量**：对测试覆盖边界的认识。
**好答案的样子**：
- 测试覆盖的是「你想到的路径」，生产的差异在数据量、并发、超时、权限、脏数据、部分失败、真实网络。
- 上线前要能回答三件事：出问题怎么发现（监控/告警）、怎么回滚、影响面多大；灰度/金丝雀比一次全量可信。
**要警惕**：把「测试通过」等同于「没问题」。

## 四、协作、学习与自省（15–18）

### 15. Code review 里有人给你提了一条你认为不对的意见，你怎么办？
**想量**：对事不对人的能力。
**好答案的样子**：
- 先复述对方的顾虑，确认双方说的是同一件事；再讲自己的约束和证据。
- 请对方指出「什么情况下我会错」，把争论变成可验证的问题。
- 风格问题服从项目约定，正确性问题看证据；对方对了就明确承认。
**要警惕**：表面接受背后不改；用「一直这么写的」当理由。

### 16. 接手一份没有文档的老代码，你第一步做什么？
**想量**：是否先建立可运行的事实基础。
**好答案的样子**：
- 先让它跑起来：能启动、能跑测试、能打通一条主链路。
- 再顺一条真实请求从入口走到数据库，画出调用关系；用最小改动去验证自己的理解。
- 边看边补文档，把「我确认过的事实」留下来。
**要警惕**：先大改结构；只读代码不运行。

### 17. 你怎么判断自己「真的懂了」一个东西？
**想量**：元认知。
**好答案的样子**：
- 能用自己的话讲给外行听；能说出它的边界和失效条件；能预测改动的后果并被验证；能指出它不适合什么场景。
- 知道「能跑通」和「懂原理」是两件事。
**要警惕**：把复述步骤当成理解；只记得结论记得住原因。

### 18. 讲一个你当时觉得对、后来发现错了的技术决定。
**想量**：复盘能力，以及是否诚实。
**好答案的样子**：
- 讲得出当时的信息、当时的推理、后来什么证据推翻了它、现在会怎么做得不同。
- 重点是有没有沉淀成一条可复用的规则。
**要警惕**：举不出例子（可能从没复盘过）；把责任全推给别人或环境。

## 五、责任与安全（19–20）

### 19. 一个任务你完全不会，但两天内必须交付。你怎么走？
**想量**：拆解能力与「说不会」的勇气。
**好答案的样子**：
- 先拆出「必须能跑的最小切片」，找现成实现或官方示例，而不是从零造。
- 明确告诉对方哪些是临时方案、风险在哪、什么时候补齐；不会的部分早点提出来换方案或换人。
**要警惕**：硬扛到最后一天才说；抄来不理解就上线。

### 20. 你凭什么认为你这次的改动是安全的？
**想量**：「安全」在他脑子里是不是一个具体的东西。
**好答案的样子**：
- 说得出验证手段（自动化测试、关键路径手测、灰度观察哪些指标）。
- 说得出失败时的回滚路径、影响面（谁在用、出问题谁受影响）、最坏情况是什么。
- 安全不是「我测过了」，而是「我知道它可能怎么坏，坏了能多快恢复」。
**要警惕**：「我本地试了没问题」。

## 附一：怎么用这 20 题

不必全问。30–40 分钟挑 6–8 道，从第一部分开始（排障题最能量出真实经验），后面按岗位侧重调整：偏后端的多问 5/10/11/13，偏前端的多问 3/8/14。

每道题至少追问两次：
1. 「为什么先做这个，不是那个？」——看优先级是否有依据。
2. 「还有别的可能吗？你怎么排除它？」——看是否真的在推理，而不是背了一套流程。

语言/框架基本功不必单独出题，从排障题的表述里自然能听出来；如果连术语都用错，说明基础还没到。

## 附二：评分维度

| 维度 | 看什么 | 典型红旗 |
| --- | --- | --- |
| 证据意识 | 先观测再下结论；会设计验证 | 靠猜、靠改代码试探 |
| 边界意识 | 想到失败、并发、数据量、部分成功 | 只考虑顺利路径 |
| 取舍能力 | 说得出代价和适用条件 | 只有「更好/更快」没有「更贵」 |
| 自省能力 | 知道自己的假设可能错 | 从没复盘过，永远不是自己的问题 |
| 表达 | 能把复杂问题讲清楚 | 堆术语，讲不出因果 |
